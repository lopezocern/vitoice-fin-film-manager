## 一、严重问题(建议立即修复)

### S1. poster/thumbnail 路径任意写入 → 任意文件读取与删除【安全,高危】✅ 已修复

- **位置**: `backend/app/schemas/media.py:87-88` + `backend/app/api/media.py:337-339, 1100-1114, 1179-1201` + `backend/app/api/recycle_bin.py:36-45, 212-277`
- **问题**: `MediaUpdate` 允许客户端直接写 `poster_path` / `thumbnail_path` 两个任意字符串字段;`update_media` 用 `model_dump(exclude_unset=True)` + `setattr` 原样落库,无任何路径校验。随后:
  - `GET /media/{id}/poster`(1100)与 `/thumbnail`(1083)对 `FileResponse(str(path))` **任意文件读取**;
  - `DELETE /media/{id}/poster`(1179)、`recycle_bin._cleanup_asset_files`(36-45)与 `permanent`/`empty`(212-277)对 poster/thumbnail 路径执行 `unlink()` **任意文件删除**。
- **影响**: 知道媒体 ID 的请求方可将 `poster_path` 指向任意文件 → 读取系统任意文件内容;或指向任意文件 → 删除任意文件(含库文件)。配合 S6 无鉴权 + `0.0.0.0` 监听,可被远程利用。
- **修复**: 落库前 `Path(poster_path).resolve()` 后校验必须位于 poster 目录 / thumbnail 目录内;或移除这两个字段的客户端可写性,改为服务端内部管理。

### S2. 字幕 file_path 任意路径 → 任意文件读取【安全,高危】✅ 已修复

- **位置**: `backend/app/api/subtitles.py:49-65(create)、96-124(get_content)、19-34(_validate_path)`
- **问题**: `_validate_path` 仅拦截 `..` 路径遍历与符号链接,但**不限制绝对路径**。`create_subtitle` 的 `file_path` 未限定在媒体所在目录,`get_subtitle_content` 可返回任意绝对路径文件的文本内容。
- **影响**: 任意文件文本泄露(如 `C:\Users\...\secrets`、配置、私钥)。
- **修复**: 校验 `file_path` 必须位于该媒体文件所在目录或其子目录内(用 `resolve()` 后做 `is_relative_to` 检查)。

### S3. 迁移 012 未更新 media_type 枚举约束 → 生产库写入 OFFLINE 必失败【数据,高危】❌ 误报,不改

- **位置**: `backend/alembic/versions/012_add_file_missing.py:22-40`(对照 `001_initial.py:45` 与 `004_fix_tasktype_check_constraint.py`)
- **问题**: 001 迁移为 `media_type` 生成了 `sa.Enum("local","network","both")`(SQLite 下为 `CHECK (media_type IN (...))` 约束)。项目自身在 002/004 迁移中已明确"SQLite 的 Enum 是 VARCHAR+CHECK,必须用 `batch_alter_table(recreate="always")` 重建表才能更新",但 012 只是加了列,注释声称"SQLite 不强制 CHECK"——**与自身认知矛盾**。迁移后的生产库 CHECK 约束仍只有 `('local','network','both')`。
- **影响**: `scanner.py:271`、`file_watcher.py:479,523`、`libraries.py:811` 均写入 `media_type=OFFLINE`,在走迁移升级的库上会抛 `CHECK constraint failed`,文件缺失检测、离线媒体、软删除全链路不可用。dev 库因 `create_all` 按模型含 offline 故未暴露。
- **修复**: 012 需用 `batch_alter_table(recreate="always")` 重建 media 表以更新 CHECK 约束。

### S4. 目录重命名/删除的前缀匹配无边界 → 兄弟目录数据错乱【数据,高危】✅ 已修复

- **位置**: `backend/app/api/libraries.py:720, 725, 800` + `backend/app/services/file_watcher.py:507, 553`
- **问题**: `Media.file_path.like(f"{old_dir}%")` 前缀无路径分隔符边界。重命名/删除 `C:\Movies\Show` 会连带把 `C:\Movies\Show2\*.mp4`、`C:\Movies\Showtime\*.mp4` 等兄弟目录的媒体路径一并改写(`file_path[len(old_str):]` 得到损坏路径)或误标 `file_missing`。
- **影响**: 目录操作后大量媒体路径损坏、文件被误判缺失,系列/刮削/播放连锁错乱。
- **修复**: 前缀拼接 `old + os.sep`(并排除精确目录本身),删除分支同样处理。

### S5. TaskManager cancel 竞态:CANCELLED 被 RUNNING 覆盖【逻辑,高危】✅ 已修复

- **位置**: `backend/app/tasks/manager.py:262-297(_run_worker 置 RUNNING 前不检查状态)`
- **问题**: `cancel()` 对 PENDING 任务先把 DB 状态置为 CANCELLED;但 `_dispatch_loop` 入队后 `_run_worker` **无条件**执行 `task.status = RUNNING`,覆盖 CANCELLED 后继续执行。完成阶段虽有 CANCELLED 检查(346),但启动阶段没有。
- **影响**: 用户取消的扫描/刮削/打标任务继续跑完,任务状态最终显示 completed,取消功能失效。
- **修复**: 置 RUNNING 前先查 `status == PENDING`,否则直接释放信号量返回。

### S6. 全部 API 无鉴权 + 无 SSRF 防护【安全,高危】

- **位置**: `backend/app/main.py:82-86(VITOICE_HOST=0.0.0.0)`;`backend/app/api/media.py:851-896(stream_network_media 代理任意 URL)`;`backend/app/services/adult_source.py`(page_url 由 base_url + code 拼接,code 含 `/` 可路径注入)
- **问题**: 全部 API 无任何认证;`stream_network_media` 代理客户端传入的任意 URL,无 scheme/内网地址校验;`adult-resolve` 的 `base_url` 可指向任意主机构造任意出站请求;`extract_network_metadata` 把 URL 直传 ffprobe。
- **影响**: 与 S1/S2 叠加,监听 0.0.0.0 时所有漏洞可远程利用;亦可作为 SSRF 跳板访问内网。
- **修复**: 至少加 URL scheme 白名单(http/https)与内网 IP 拦截;长期引入简单 token 鉴权。

### S7. 受限内容 / 软删除 IDOR:详情、流、缩略图等端点均未过滤【安全,高】

- **位置**: `backend/app/api/media.py:298(GET /media/{id})、658(/stream)、1083(/thumbnail)、1100(/poster)`;`series.py:81`;`smart_folders.py:71(preview 无 is_deleted/受限过滤)`
- **问题**: `get_restricted_library_ids` 只用于 list/search/stats 等列表接口;上述按 ID 访问的端点不校验 `is_restricted`、`is_deleted`。
- **影响**: 知道 ID 即可绕过受限内容开关直接流式播放/查看封面;软删除的媒体仍可被访问。
- **修复**: 统一抽一个依赖项,对单个资源访问做受限库/软删除过滤。

### S8. 并发刮削重复创建 Series + episode_count 恒滞后【逻辑,高】

- **位置**: `backend/app/services/scraper.py:925-1006`
- **问题**: (1) 查询-再创建无唯一约束(`tmdb_id + library_id`),并发 worker 可重复建 Series;(2) 既有 Series 的 `episode_count` 计数查询(997-1003)在 `media.series_id = series.id`(1006)赋值**之前**执行,本集不计入,计数恒滞后 1。
- **影响**: 系列页出现重复剧集条目;集数显示永远少 1。
- **修复**: 加唯一约束;计数移到赋值之后(或直接 `SELECT COUNT(*)` 在提交前重算)。

### S9. ai_tagger `unverified_only` 参数被静默忽略 → 全量重复 AI 打标【性能/成本,高】

- **位置**: `backend/app/services/ai_tagger.py:321-357`
- **问题**: 查询(335-342)只过滤 `media_type != NETWORK` 与 library,**从未把 `unverified_only` 放进 WHERE**;配合 `fetchall()` 全量加载,每次批量打标任务都会对全库(含已验证媒体)重复调用 AI 接口。
- **影响**: AI 打标任务耗时与 API 成本失控,重复打标污染数据。
- **修复**: 按 `~exists(VideoTag where is_verified=false)` 过滤,或至少 `and_(VideoTag.is_verified == False)` join 过滤。

### S10. re_scrape / re_tag 任务标志跨会话提交竞态【逻辑,中高】

- **位置**: `backend/app/api/libraries.py:303-306, 357-360`
- **问题**: 任务由 `enqueue()`(独立会话已 COMMIT,result=NULL)后,本请求会话才写 `task.result` 并 flush(依赖结束时才 commit)。dispatch 可能在 commit 前读到该任务 → worker 读 `result=None` → `re_scrape`/`re_tag` 标志静默丢失。
- **影响**: 手动触发"重新刮削/重新打标"偶发不生效。
- **修复**: 入队前在同一事务写标志再 commit;或 worker 内直接读 settings 判断。
