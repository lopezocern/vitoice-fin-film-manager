### ⚠️ 对 v1 的一处修正：请求数不是 21

v1 写的"首屏 21 请求 / 4000 行"是**代码上限**（`page <= 20` × `page_size=200`），不是实测值。
在 **dev 库 874 条媒体** 的真实规模下：

```
页数 = ceil(874 / 200) = 5 次请求
```

所以准确表述是：

| 媒体总量 | 实际请求 | 拉取条目 | 结果 |
|---|---|---|---|
| 874（当前 dev） | **5** | 874 / 874 | 正确但浪费 |
| 4,000 | 20 | 4000 / 4000 | 恰好到上限 |
| **> 4,000** | 20（循环终止） | 4000 / N | **静默截断**——问题清单少算 |

也就是说：**当前规模下是"浪费"，规模上去之后是"算错"**。后者才是必须修的原因。

### 2.4 概览页删除后的数据落点（关键，别丢能力）

`OverviewView` 独占三份数据，实测确认**全前端只有它消费**：

| 数据 | 来源字段 | 现状 | 新落点 |
|---|---|---|---|
| 库健康（每库媒体数、缺失数、容量） | `stats.library_health[]` | 仅概览 | **`/libraries` 扩展返回**（见 §3.4），由 `LibrariesStatusView` 展示 |
| 运行中的工作 | `stats.summary.running_tasks` + `/tasks` | 概览 + 任务页 | 侧边栏徽标 + `RunsView`（已有） |
| 最近活动 | `/tasks`（已完成） | 概览 | `RunsView` 的 history tab（已有） |
| 媒体资产治理表 | 概览自建表格 | 概览 | **删除**，改由 `assets&view=all` + 顶部摘要条 |

### 3.4 `GET /libraries` 扩展（决策 1 的必要条件）

> **更正（PR1 实施时发现）**：`LibraryResponse` **已有** `media_count`（`schemas/library.py:79`），
> v1/v2 初稿写"没有"是错的。真正缺的是 `missing_count` 与 `total_size`。

`media.library_id` 上的现有单查询已带 `count(Media.id)`，只需补两个聚合；仍是 1 条 SQL、无 N+1。
**`media_count` 的既有语义保持不变**（含软删除行），以免改变现有库徽标数字。

```python
query = (
    select(MediaLibrary, *_library_aggregates())
    .outerjoin(Media, MediaLibrary.id == Media.library_id)
    .group_by(MediaLibrary.id)
    .order_by(MediaLibrary.created_at)
)
```

其中：

```python
def _library_aggregates():
    return (
        func.count(Media.id).label("media_count"),
        func.coalesce(func.sum(Media.file_size), 0).label("total_size"),
        func.coalesce(
            func.sum(case((Media.file_missing == True, 1), else_=0)), 0  # noqa: E712
        ).label("missing_count"),
    )
```

`library_health` 字段在 `/stats` 里保留（不删），但前端不再依赖。

media      : file_missing ✓  series_id ✓  metadata_ignored ✓  library_id ✓
video_tags : ix_video_tags_media_id ✓  uq(media_id, tag_id) ✓
