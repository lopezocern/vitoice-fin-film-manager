## 二、P0 组设计(纯增量、低风险、建议先做)

### D1. 预置系统智能文件夹(替代 R12 的"预置文件夹"诉求)

**现状**: smart_folders 全为用户自建;规则引擎已支持 8 维度(标签/评分/时长/分辨率/文件大小/来源类型/资源库/季数/集数),缺 `playback_position`、`last_played_at` 两个维度与预置入口。

**后端设计**:
1. **新规则维度** `handlers.py` 增加两个 handler(遵循现有注册机制,open/closed):
   - `PlaybackHandler`(`dimension="playback"`):`gt/eq/is_null`,作用于 `Media.playback_position` — 服务"继续观看"。
   - `WatchedHandler`(`dimension="watched"`):`eq` 作用于 `Media.is_watched` — 服务"未看/已看"。
   - 注意:`Media` 模型当前**无 `last_played_at` 字段**(只有 `is_watched`/`playback_position`),按现有数据设计,不新增字段。
2. **预置文件夹初始化** `smart_folders.py` 增加 `init_system_folders(db)`(幂等,按名称查重,`is_system=True` + `sort_order` 负值置顶):
   - 全部媒体 / 视频 / 网络媒体 / 本地缺失 / 未看 / 继续观看(playback_position>0)/ 最近添加(created_at 7 天)/ 未分类(无标签)/ 回收站
   - 预置文件夹的 `rule_json` 直接用现有引擎的规则树 JSON 格式(与用户自建完全一致,前端无需区分)。
3. **API**: `GET /smart-folders` 在 list 时调用 `init_system_folders`(与 video_mana 同思路,懒初始化,避免迁移)。

**前端设计**:
- `smart-folders/+page.svelte` 列表顶部自然显示预置项(`is_system=true` 时隐藏删除按钮、限制编辑);DIMENSIONS 配置表加 `playback`、`watched` 两项(供用户自建时也可用)。
- 侧边栏 `MediaSidebar.svelte` 的"智能"分组无需改——预置项会随列表接口出现。

**风险**: 预置文件夹与用户已建同名文件夹冲突 → 初始化按名称查重跳过;`is_system` 标记仅影响 UI 删除限制。
**工作量**: 后端 ~120 行,前端 ~60 行。

### D2. 智能选帧(视频封面跳过空白帧)

**现状**: `backend/app/services/thumbnail.py` 固定 `settings.thumbnail_time_offset=10s` 截一帧,无空白帧判断。

**后端设计**:
1. `thumbnail.py` 生成缩略图时改为**多候选帧采样**:
   - 候选时间点:`[2%, 10%, 25%, 50%]` × 时长(或 `[2s, 5s, 10s, 30s, 时长50%]`),取前 N 个有效帧。
   - 用 `ffmpeg` 的 `select='not(between(t,0,1))'` 或对候选帧做**亮度/方差检测**(PIL 读帧 → 灰度 → 标准差 > 阈值即"有效",跳过黑屏/纯色)。
   - 命中有效帧即用,全部无效则回退默认 offset。
2. **新增设置**: `thumbnail_smart_frame: bool = True`(settings 表 + 设置页"缩略图"分区),与现有 `thumbnail_size/quality/time_offset` 并列。
3. 性能:智能选帧只在**首次生成**时执行(现有缓存逻辑不变);批量缩略图任务逐媒体跑,不增加额外并行压力。

**前端设计**:
- 设置页"缩略图"分区加"智能选帧(跳过黑屏帧)"开关,`PUT /settings` 已有通用保存链路,无需新端点。

**风险**: 低。回退逻辑保证永远有封面。注意 ffmpeg 帧采样次数增加 → 单媒体耗时略增(首次),可接受。
**工作量**: 后端 ~100 行,前端 ~20 行。

## 三、P1 组设计(中等改动,建议第二批)

### D5. 增量扫描增强:file_size_cached 双字段 + 跳过未变文件

**现状**: scanner.py:198 已比较 `file_modified_at`,变化时重建 `to_update`(只更新时间戳和大小);但**无 `file_size_cached` 字段**,mtime 可能因权限/拷贝等原因未变而内容已变,且扫描对未变文件仍遍历全量。

**后端设计**:
1. **迁移**: `alembic` 新增一版,`media` 表加 `file_size_cached: int | None` 列(与 video_mana 同语义)。纯增量、可空,无数据迁移风险。
2. **scanner.py 改造**:
   - Phase 3 加载 `file_size_cached`;Phase 4 判断:`file_modified_at == mtime && file_size_cached == size` → 完全跳过(不重建 to_update);
   - 变化时更新 `file_size_cached` 与 `file_size`。
   - 新记录创建时写入 `file_size_cached = file_size`。
3. 由于 vitoice 的扫描本就把"全量比对"作为设计(用于缺失检测),此改动**不改变扫描遍历范围**,只减少 DB 更新量 —— 真正的大库收益需配合 D6(见下)。

**前端**: 无改动(纯后端优化)。
**风险**: 低。字段可空,旧记录首次扫描自动补填。
**工作量**: 迁移 ~30 行,scanner ~40 行。

### D6. 重命名/移动识别:hash 索引合并(解决 watcher 事件丢失)

**现状**: 依赖 file_watcher 的 moved 事件更新路径;应用关闭期间文件被改名/移动 → 扫描产生"旧记录 missing + 新记录重复"。

**后端设计**(在 D5 基础上):
1. **迁移**: 同一版加 `file_hash: str | None`(64KB blake2b 前缀哈希,与 `compute_file_hash` 一致)+ 索引。已有 `file_hash` 字段?—— **核对:Media 模型当前无 file_hash 字段**(`compute_file_hash` 只用于去重但未落库)。故新增列。
2. **scanner.py 增量逻辑**:
   - Phase 3 额外加载 `Media.id, file_hash, file_path`(全库非 deleted、非 missing);
   - Phase 4 对新路径:先查 path 不存在 → 算 hash → 若 hash 命中已有记录且路径不同 → 判定"重命名/移动":更新该记录 `file_path/file_name/file_modified_at/file_size_cached/file_missing=False`,并从 `existing` 移除旧路径(避免 Phase 5 误标 missing);
   - 记录 `resurrected_paths`(与 video_mana 同思路)供缺失检测排除。
3. **性能**: hash 只对"新路径"计算(每文件一次 64KB 读),可接受;内存中维护 hash→id 映射,大库注意用 dict 而非逐条查。

**前端**: 无改动(扫描统计自动体现,new/updated 计数语义不变)。
**风险**: 中。hash 计算增加扫描耗时(每新文件 ~1ms 级);需处理 hash 冲突(同 hash 多记录时取最早未删除者)。建议该功能与 D5 同版迁移,一次性改 scanner。
**工作量**: 迁移 ~20 行,scanner ~90 行。

### D7. 感知哈希相似检测(图片/海报视觉去重)

**现状**: `perceptual_hash.py` 仅 `find_duplicates`(精确对,返回 (id1,id2,score)),无阈值分组、无 UI。

**后端设计**:
1. **扩展 `perceptual_hash.py`**(参考 video_mana,但适配 async SQLAlchemy):
   - `find_similar_groups(hashes: list[tuple[int, str]], threshold=0.93) -> list[list[int]]`:向量化 XOR + popcount 分块(块 2000)+ 并查集分组,返回组内媒体 id。
   - 计算函数 `compute_perceptual_hash` 已有(对缩略图),确认仅用于缩略图 —— **设计决定:对 `thumbnail_path` 对应的 jpg 计算 dHash**(图片类媒体用原图,视频用缩略图),存 `perceptual_hash` 字段。
2. **迁移**: `media` 表加 `perceptual_hash: str(16) | None` + 索引。
3. **新端点** `media.py`(或新 `media_dup.py`):
   - `GET /media/similar?threshold=0.93&limit=50` → 分组列表(每组:count + 成员 id/title/thumbnail/file_size);
   - `POST /media/similar/skip` `{media_ids}` → 置 `similar_skip=true`(迁移加该列);
   - `POST /media/similar/reset-skip`。
   - 计算为 CPU 密集 → `asyncio.to_thread` 包裹,一次性内存加载所有哈希(与 video_mana 同,需限 limit 或分页)。
4. **存量回填**: 设置页提供"计算感知哈希"后台任务(复用 TaskManager,新 TaskType 或复用 THUMBNAIL),逐媒体算哈希入库。

**前端设计**:
- 管理页新增"相似内容"入口(或标签 Tab 扩展):展示分组卡片(缩略图+大小),组内可"跳过此组""标记非相似"。
- 设置页"数据库"分区加"计算感知哈希"按钮(异步任务,任务抽屉可见进度)。

**风险**: 中。首次计算全量哈希是重任务(须任务化);dHash 仅对图片类高精度,视频缩略图相似性有限 —— 建议**首期仅对图片类媒体开放** UI,视频仅存哈希不上 UI。
**工作量**: 后端 ~200 行,前端 ~150 行,迁移 ~15 行。

### D8. watcher 目录事件优先 + 子路径去重

**现状**: `file_watcher.py` 的 `_on_file_appeared/_stable_check` 对单文件处理;目录 moved 走 `_update_dir_paths`,但**事件队列无排序**,文件级 moved 与目录级 moved 可能重复处理同一批文件。

**后端设计**(参考 video_mana `_process_events`):
1. `file_watcher` 事件处理增加**目录优先 + 已处理路径去重**:
   - 把 watchdog 事件先入内存队列(复用现有 debounce),处理时排序:dir 事件在前、file 事件在后;
   - 维护 `handled_paths` 集合:目录 moved/deleted 处理后,跳过所有以该目录为前缀的文件事件;
   - 扫描进行时挂起队列处理(现有 `_schedule_scan` 已有此意图,明确为"扫描期间丢弃/延后事件")。
2. 纯逻辑改动,无迁移。

**前端**: 无改动。
**风险**: 低。事件合并策略是纯增量,行为仅在"目录操作"场景改变(减少重复处理),单文件场景不变。
**工作量**: 后端 ~80 行。

- **前端**: FilterBar 增加颜色筛选下拉(取缩略图主色),管理页可选。
- **工作量**: 后端 ~100 行,前端 ~60 行。依赖 D7 的哈希任务一并回填(或独立任务)。
- **依赖**: 与 D7 共享"媒体增强字段"迁移,建议同批。

### D10. 启动对账 reconcile

- **后端**: `main.py` 启动时后台线程执行轻量对账:遍历库路径 ↔ DB 记录(不重算 hash),差异 >50 触发全扫,否则增量;补 `file_missing` 状态;可选补缩略图/哈希缺失。
- **前端**: 无。任务抽屉可显示"启动对账"进度。
- **风险**: 需避免与 file_watcher 启动扫描竞争(对账期间挂起 watcher)。
- **工作量**: 后端 ~180 行。

### D11. 批量物理移动(跨库)+ 冲突处理

- **现状**: batch.py `_batch_move` 只改 `library_id`;libraries.py 有库内物理移动。
- **设计**: `_batch_move` 增加 `physical: bool` 参数:true 时校验目标库 root,`shutil.move` 物理移动 + 冲突后缀 + 更新 file_path/folder;false 保持纯逻辑移动。前端移动对话框加"同时移动磁盘文件"复选框。
- **工作量**: 后端 ~80 行,前端 ~40 行。

### D12. 恢复本地文件关联(original_local_path)

- **现状**: delete-local-file 后记录 OFFLINE;若文件重新出现,scanner D6 的 hash 合并可自动恢复(设计已覆盖);无需单独字段。
- **结论**: D6 落地后此项自动满足,不单独设计。

## 六、实施顺序建议与总览

```
批次1(P0,纯增量,约 1-2 周)
  D1 预置智能文件夹        → 后端 120 + 前端 60
  D2 智能选帧              → 后端 100 + 前端 20
  D3 孤立缩略图清理        → 后端 80 + 前端 50
  D4 重命名冲突自动后缀    → 后端 30 + 前端 30
批次2(P1,迁移 A,约 1-2 周)
  D5 增量扫描双字段        → 迁移 30 + 后端 40
  D6 重命名/移动识别       → 迁移 20 + 后端 90
  D8 watcher 事件去重      → 后端 80
批次3(P1,迁移 B,约 1-2 周)
  D7 感知哈希相似检测      → 迁移 15 + 后端 200 + 前端 150
  D9 主色调筛选            → 后端 100 + 前端 60(依赖 D7 回填)
批次4(P2,按需)
  D10 启动对账             → 后端 180
  D11 批量物理移动         → 后端 80 + 前端 40
  D12 恢复关联             → 由 D6 自动满足,不单列
```

**决策点(建议审阅时明确)**:
1. **批次 1 是否立即开工?**(D1-D4 全是纯增量,风险最低)
2. **D6 hash 合并**是否值得 scan 耗时增加(每新文件一次 64KB 读)?若你的库主要是增量小文件,推荐;若超大库且扫描频率高,可先只做 D5。
3. **D7 相似检测**首期仅限图片类媒体(精度可靠),视频仅存哈希不上 UI —— 是否接受此范围裁剪?
4. **D3 缩略图分片**:当前库已平铺,不迁移,仅加清理工具 —— 是否接受?(分片对 1 万+文件的新库才有明显价值)
5. 所有批次均**不改变现有 API 契约**(新增端点/字段均为向后兼容),符合"不影响正常功能"原则。
